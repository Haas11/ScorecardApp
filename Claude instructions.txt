GROUP 5 - GRID DETECTION REDESIGN (design session only, no coding spree)
------------------------------------------------------------------------
[~] #16 Grid detection misplaces lines even on clean aligned scans; eventual goal is normal
        photos. Reconsider the approach (e.g. template/homography, line-model fitting,
        VLM-assisted corner finding) and agree on a design before implementing.
          2026-09-28 (Opus): design proposed below, NOT implemented. Safety net built first:
          test_grid.py + grid_golden.json snapshot the detected row/col boundaries of the two
          hand-verified games (Grizzlies 07-12, Urbanus 08-23); any detector change must stay
          within 4% of a cell (~5px) there. Offline, no API. `uv run python test_grid.py`.

          WHY THE CURRENT APPROACH BREAKS: probe_grid projects the whole thresholded image onto
          the x and y axes. That assumes (a) zero rotation/perspective (a 1 degree skew smears a
          2700px line over ~47px of the other axis), (b) one global cell_size, (c) a fixed global
          threshold of 180 (fails on shadows/uneven light), (d) heuristics for which peak is the
          header (Layout A/B, bimodal gaps, pair-merging) that are tuned per card. Manual flags
          (--grid-start/--grid-width/--left-skip/--cell-height) patch symptoms. None of this
          can work on photos.

          PROPOSED DESIGN: register against a known template instead of discovering the grid.
          The KNBSB card is a fixed printed form, so the grid is known up to a warp.
          1. Template (one-time): canonical card model in normalized units: batting-grid outer
             rectangle, header half-row, 10 player rows (with sub-row line), 12 inning cols
             (with sub-col line), 2 totals rows. Measured once from the Grizzlies scan.
          2. Find the grid frame: grayscale -> adaptiveThreshold (lighting-robust) -> long-line
             extraction (morphology in rotated kernels, or cv2 LSD) -> fit the 4 outer edges of
             the inning grid (left edge of col 1, right edge of col 12, header top, totals
             bottom) -> 4 corners. Fallbacks, in order: --corners x1,y1,...,x4,y4 manual
             override (replaces the 4 current geometry flags), then optional VLM corner
             query (one Gemini call per game).
          3. Rectify: cv2.getPerspectiveTransform + warpPerspective to a canonical image
             (e.g. 140 px per cell). All crops (cells, name strip, totals) are taken from the
             rectified image, so skew/perspective disappears and the grid is known by
             construction.
          4. Refine locally: for each expected line in the rectified image, search +-15% of a
             cell for the projection peak within that line's own band only, and snap. This
             absorbs print tolerance and mild paper bend. Photos with a curled page may need
             piecewise warps per row band (phase 3 only).
          5. Validate, fail loudly: grid_score = share of expected lines found within
             tolerance, plus spacing regularity. Below the threshold, stop and ask for --corners
             (or the VLM fallback) instead of silently cropping wrong cells. Store the score in
             _layout.json.
          6. Persist corners + refined lines in _layout.json (run_args style, #17), so
             --reuse-cache / crawl never re-detect differently.

          PHASES (one per session): P1 frame+homography+validation on scans, keep old
          detect_grid as fallback behind a flag; must pass test_grid.py (compare in original
          image coords via the inverse homography). P2 local refinement, and add Vennep Flyers
          06-28 (the manual-override game) to the golden once its grid is visually verified.
          P3 phone photos (needs 2-3 sample photos). P4 VLM corner fallback.
          Also helps #8 (neighbour-cell reads): rectified cells are exact squares, so the
          2x2 quadrant split becomes reliable.
